## Production sign-in blocker — Not fixed

This is a concrete contract incompatibility, separate from the working local authentication fixture:

- `apps/mobile/src/auth/handoff.ts:1,14,21` hardcodes `caseops://oauth/callback` in authorization and requires that exact custom scheme in callback parsing. `apps/mobile/App.tsx:239` also sends that callback in exchange.
- `apps/api/src/caseops_api/core/settings.py:119–126` defaults native issuance/signing off, leaves the native signing key unset and the redirect registry empty.
- `apps/api/src/caseops_api/core/native_auth.py:43–70` requires enabled native controls, a separately provisioned signing key and registered **HTTPS** callbacks in non-local environments. It rejects the client's current custom scheme. Enabling flags alone cannot repair this.
- `app.config.ts` contains neither iOS `associatedDomains` nor Android HTTPS `intentFilters` for a production callback.

Choose the real production HTTPS callback only after organization/domain/IDs are established. Implement and prove the matching client callback/parser, backend exact registry, iOS associated-domain entitlement and `apple-app-site-association`, plus Android verified intent filters and `/.well-known/assetlinks.json`. Bind association data to the actual Apple application identifier/team and the **Play-distributed signing certificate**, not a Simulator prefix, debug certificate or upload-key assumption. Follow [Apple universal links](https://developer.apple.com/documentation/xcode/supporting-universal-links-in-your-app) and [Android verification](https://developer.android.com/training/app-links/verify-applinks).

Retain PKCE, state binding, single-use codes, separate native token realm, MFA, strict TLS and logout/revocation fences. A production callback must pass real end-user verification on both signed platforms before any enablement/deployment claim. No flags or auth policy were weakened in this review.
