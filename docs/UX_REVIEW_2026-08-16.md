# CaseOps UI/UX review — 2026-08-16

Scope: the signed-in application, `apps/web/app/app` — 74 pages, ~44,000 lines,
33 navigation destinations. Reviewed against `.impeccable.md` and the five
journeys it names.

The brief was: users should have no confusion using this. This review is
evidence-first — every finding below is a file and a line, not an impression.

---

## Is `impeccable` the constraint?

**No, and it is worth being precise about why**, because the instinct to blame
the design system would send the next change in the wrong direction.

`impeccable` governs *aesthetics* — typography, OKLCH colour, spacing rhythm,
density, motion. Every P0 defect below is an **affordance** failure: a control
that does not tell you what it wants, or shows you a value you cannot read.
The skill does not cause those. It explicitly forbids them:

> *"Keep important actions obvious."*
> *"Design empty states that teach the interface."*
> *"Every primary action has a keyboard path."*

The real constraint is different, and it is architectural: **these screens were
built API-first.** A form field exists for each field the endpoint accepts, in
the endpoint's vocabulary. `POST /deadline-coverages` takes
`responsible_membership_id`, so the UI grew a text box labelled *"Primary
membership ID"*. That is a faithful rendering of the API and a useless rendering
of the task, which is *"who is covering this deadline?"*

So the way out is not to relax the design system. It is to make each screen
model the **user's question**, then bind that to whatever the API needs. That is
what the P0 fix in this PR does, and it is the pattern the rest should follow.

One genuine gap in the skill: it has no guidance for **choosing an entity**
(a person, a matter, a docket). That is the single most common interaction in
this product. This PR establishes the house pattern; the skill should absorb it.

## P0 — the workflow is not operable. Implemented in this branch; not released.

### 1. Ten controls required the user to type a membership UUID

| File | Control |
|---|---|
| `app/ip/page.tsx` | Primary membership ID, Backup membership ID |
| `app/ip/page.tsx` | Current membership ID, Replacement membership ID |
| `app/ip/page.tsx` | Owner membership ID, Second approver membership ID |
| `app/ip/page.tsx` | Independent fixture reviewer membership ID |
| `app/admin/employees/page.tsx` | Manager membership ID (create **and** edit) |
| `app/admin/notifications/page.tsx` | Replacement membership ID |

No lawyer knows that `b05ca0d9-a2e5-42de-b315-acdbc4b1c6a3` is Priya. These
controls could only be operated by someone reading the database. Deadline
coverage — who is accountable if a filing date is missed — was gated behind a
UUID.

The root problem was that these forms exposed API identifiers instead of a
tenant-scoped entity choice. They needed one shared picker contract that works
for ordinary authenticated workflows as well as employee administration.

**Fixed:** a house `PersonPicker`, applied to all ten controls: seven IP
controls, two employee-manager controls, and one notification control.

### 2. The responsible person was displayed as a UUID

`app/ip/page.tsx` rendered `Responsible: {row.responsible_membership_id}`. The
one fact that matters on a coverage row — *who holds this* — was unreadable.

**Fixed:** `PersonName` resolves the id to a name, and falls back to the id
rather than a blank when it cannot resolve, because an unresolved reference is
more honest than an empty space.

## P1 — the user hesitates or picks wrong. Implemented here where noted; deeper Today consolidation remains open.

### 3. Six destinations answer "what do I need to do?"

`Home`, `Today`, `Hearings`, `Cause list`, `Calendar`, and `Deadline control`
all answer a version of the same morning question:

| Destination | Answers |
|---|---|
| Home | "what's coming up" |
| Today | "what demands attention today" |
| Hearings | "this week / next 30 days" |
| Calendar | month grid |
| Cause list | tomorrow's court list |
| Deadline control | IP deadlines and who holds them |

A lawyer arriving in the morning has six plausible starting points and no signal
which is authoritative. `.impeccable.md` names journey one as *"open the
workspace in the morning, scan hearings this week"* — the product cannot say
where that starts.

**Implemented in this branch; not released:** grouping now says what the flat
list could not. `Today` sits alone with `Home` under *Overview*; `Hearings`,
`Cause list` and `Calendar` cluster under *Schedule*, which reads as
**renderings of a timetable** rather than three competing to-do lists;
`Deadline control` sits under *Intellectual property*, where its scope is
obvious.

**Corrected 2026-08-16, and this one mattered because work was about to be built
on it.** I wrote that `Today` should "absorb hearings-this-week and due
deadlines". It already did: `Today` aggregates five streams — hearings 7d,
deadlines 7d, tasks due/overdue, drafts in review, overdue invoices — with
server-side caps and a truncation note that already names the list views as the
unbounded source of truth. I had described a page I had not read.

A second hypothesis was also wrong and was discarded before any code: that IP
deadlines were structurally invisible because `today_view` inner-joins
`Matter.id == MatterDeadline.matter_id` while an IP-targeted deadline has
`matter_id IS NULL`. The join is real, but no production path creates a
docket-targeted `MatterDeadline` — a confirmed IP deadline projects to a
*matter-targeted* operational row and reaches `Today` today.

**The real gap, which is mine:** two personal queues built for `IPLF-039C`
never reached `Today` — a coverage transfer a colleague has offered you, and a
deadline you hold but have not acknowledged. Both are personal, time-bound and
blocking: an unanswered transfer keeps the deadline with the colleague who
offered it, and acknowledgement is what stops a critical item escalating. Both
were reachable only by opening the IP workspace and knowing to look.

**Fixed:** a sixth `Today` stream, `ip_coverage_actions`. It reuses the IP
services rather than re-querying, so IP access control has one path rather than
a second drifting copy, and it participates in the same cap/truncation contract
as the other five. A row awaiting a decision is never also listed as needing
acknowledgement — deciding is the act, and acknowledging around it would bury
the decision a colleague is waiting on.

The coverage service applies tenant visibility, lifecycle state, acknowledgement,
ordering, and the `limit + 1` probe in SQL; the cap therefore bounds database work
instead of only slicing an already-unbounded result. Lifecycle-neutralized rows
remain historical after either a Matter or IP-docket reopen and cannot reappear in
Today, workload queues, acknowledgement, or transfer decisions. Decision rows link
to the anchored accept/decline controls on the IP workspace.

**Blast radius — corrected 2026-08-16.** The relevant existing
`app-spine.spec.ts` flow clicks exactly **10** top-level labels: `Matters`,
`Today`, `Hearings`, `Research`, `Drafting`, `Recommendations`, `Contracts`,
`Outside Counsel`, `Portfolio`, and `Admin`. It also asserts that `Home` is
visible before those clicks. Regrouping preserves every one of those labels.
The navigation change is implemented, not released. A phone-width acceptance
now opens the real drawer and checks every capability-visible grouped link for
reachability, horizontal fit, navigation, and drawer close behaviour.

The lesson is worth keeping: "four files reference it" is a proxy for risk, not
a measurement of it. Counting the actual coupling took one command.

### 4. Navigation is 33 items with 17 in one group

`Work` (17), `Intelligence` (7), `Workspace` (9). Seventeen peers in a flat list
exceeds what anyone scans; the group has no internal order a user could predict.

Two are simply misfiled: **Notifications** and **User guide** are settings and
help, not daily work.

**Implemented in this branch; not released:** `Work`'s 17 became `Overview`
(2), `Schedule` (3), `Casework` (8) and `Intellectual property` (2);
Notifications and User guide moved to `Workspace` and ordered last. Largest
group is now 11 — the admin block, which is browsed rarely — down from 17. All
33 destinations are preserved.

### 5. Structured loading regions need consistent, accessible placeholders

A scoped, line-by-line inspection found structured loading regions in the
billing summary, tenant usage report, daily-docket escalations, assigned
deadline acknowledgements, hearing compliance review, and hearing
suggestion/history review. This is a bounded list of the regions changed here,
not a product-wide count inferred from grep matches. Button spinners for an
individual save, preview, or commit are a different interaction and remain.

The rule used here is narrow: **a region that will render structured content
keeps that structure while loading.** Each changed region is now a polite
`status`/live region with `aria-busy`, screen-reader loading text, and decorative
skeletons hidden from the accessibility tree. The hearing suggestion/history
region loads as two structured columns and does not announce false “no pending
suggestions” or “no history” states while its request is unresolved.

**Implemented in this branch; not released.** Focused tests pin the live-region
semantics, structured placeholders, and suppression of premature empty states.

## P2 — polish

6. ~~**Seven pages have no empty state**~~ — **false positive, withdrawn.**
   Checked individually: `admin/billing/usage` ("No usage in this period."),
   `platform-admin/provider-events` ("No provider events found.") and
   `matters/imports` ("No matching matter imports.") all have one;
   `matters/[id]/drafts/new` correctly *hides* a suggestion strip when empty;
   the document viewer has no list surface; and `account/security` and
   `admin/microsoft365` render no collection at all.

   The finding was an artefact of the detection pattern
   (`EmptyState|No .*yet|Nothing `), which missed the phrasing actually used.
   The residual point is real but minor: the existing messages are terse rather
   than teaching. That is polish on operator screens, not a confusion fix, and
   it is not worth churning copy for.

7. ~~**`app/calendar/page.tsx` hides an affordance behind hover**~~ —
   **overstated, withdrawn.** Both `group-hover:opacity` elements are
   decorative `ExternalLink` icons marked `aria-hidden`, inside a `<Link>` that
   wraps the entire row. The tap target is the row and it is always available;
   nothing is lost on iPad. A hover flourish on a decorative icon is not an
   affordance behind hover.

8. **Raw technical ids surface in operational views** — **real, and it was
   mine.** When a bulk acknowledgement partially fails, the daily docket listed
   the rejected rows as `cov-2 — Changed since you loaded this page`. The user
   had just read those same deadlines *by name* immediately above, so the
   failure report could not be matched against the list it referred to. This is
   the same defect class as P0, shipped by me the day before.

   **Implemented in this branch; not released:** the report names the deadline.
   Selection snapshots the docket title, docket identifier, deadline title,
   due date, and concurrency version. Submit freezes an id-to-label map before
   mutation, so a pending refetch, removal, or rename cannot make any rejection
   fall back to a UUID. Duplicate titles remain distinguishable.

Earlier drafts overstated the navigation blast radius and inferred loader

read as one where the P0 and the corrections were verified by hand and the

## What this branch stack implements

- `components/ui/PersonPicker.tsx` — new. Filter over a native `<select>`,
  because a firm's staff is tens of entries and a native listbox keeps the
  keyboard and screen-reader behaviour a custom combobox has to re-earn.
  Excludes people who cannot be a valid answer (you cannot transfer work to its
  current holder). Keeps a selected person visible when a filter would hide
  them, so the control never looks like it lost the selection. Inactive or
  missing historical selections remain visible as disabled current values until
  the user explicitly replaces them; explicit exclusions still clear. Says
  *"the staff list could not be loaded"* rather than failing to an empty
  dropdown that reads as "nobody works here".
- `components/ui/PersonPicker.tsx` — `PersonName` for read paths.
- Ten controls converted across three pages; labels now ask the user's question
  (*"Responsible lawyer"*, *"Offer the work to"*) instead of naming the column.
- `Field` gained an optional `htmlFor` so a composite control binds its label to
  the real input rather than to whichever box comes first.

Deadline coverage role separation is deliberately a guard-first release. Every
known create, update, proposal, acceptance, immediate-transfer, escalation, and
offboarding writer refuses a responsible/backup collision before mutation. The
database check constraint is deferred because this deployment runs Alembic
before switching the API revision; installing it now could reject writes from
the still-serving pre-guard API. A follow-up contract release will add the
constraint only after the exact guarded API revision is deployed and verified.

**Local integration verification:** the four focused billing, usage, docket,
and hearings files pass 43 tests; the full web suite passes 128 files and 642
tests; `next typegen && tsc --noEmit` is clean. The phone-width grouped-link
acceptance passes 4/4 against the local production build and API stack; the
three changed browser specs pass 7/7 together.

The IP page test previously asserted a label named *"Primary membership ID"*.
It now asserts a lawyer can pick **Priya Raghavan** by name — the test was
updated because it encoded the defect, and the new assertion is stronger.
