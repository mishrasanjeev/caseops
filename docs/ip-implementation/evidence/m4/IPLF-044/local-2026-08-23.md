# IPLF-044 local verification - 23 August 2026

## Scope

This record covers Matter linkage and synchronized but independent lifecycle
display on candidate revision
`3c94a564ca4e88bc81a414efa286d5d604612a15` (implementation commit
`a9c9962450ec8c7eb0dbd026ad2152002fccec45`). It adds one governed relationship
history and retains the existing IP docket and Matter aggregates as independent

## Implemented contract

- an additive `ip_matter_links` history with effective and retirement times,
  separate creation and retirement reasons, source, actors, and tenant-matched
  foreign keys;
- deterministic backfill of every existing `ip_docket_records.matter_id` as an
  active `operational` relationship without changing the compatibility pointer;
- one active operational Matter per docket, plus active litigation, advisory,
  appeal, enforcement, billing, and other relationships;
- optimistic concurrency, Matter-before-docket lock order, capability fencing,
  two-sided record access, duplicate rejection, and audited create/retire
  commands;
- silent omission of relationship rows, counts, and identities unless the
  reader can access both records, with an access-policy mismatch warning for an
  authorized reader;
- side-by-side Matter and IP lifecycle state in both workspaces, searchable
  Matter selection, effective-history display, and retirement controls;
- accessible IP legal events composed into a linked Matter timeline through the
  relationship's effective interval, with a source IP link and no copied Matter
  activity;
- Matter disposal/reopen no longer archives, closes, cancels, or resurrects IP
  dockets, coverage, obligations, or lifecycle state;
- updated OpenAPI client, data-governance map, user guide, law-firm page,
  machine-readable product descriptions, and canonical record-model document.

## Migration and rollback

Migration `20260823_0003` creates only the relationship table and indexes, then
reads existing docket pointers in primary-key order for deterministic backfill.
It does not update an existing row. A partial database index enforces one active
relationship per docket/Matter/role, and a second partial unique index enforces
one active operational Matter per docket even if a legacy pointer drifts.

Downgrade is permitted only while every row is an untouched migration-created
operational relationship. It refuses once manual, non-operational, or retired
governed history exists; restoration is forward-only after that point.
