## Delivered data contract

Migration `20260802_0001` is additive:

- `tracked_cases` receives last attempted, last successful, next scheduled,
  freshness, response class, last-operation, and quarantine state;
- `tracked_case_provider_operations` provides tenant-scoped record-level work with
  a unique correlation ID, provider, operation type, status, response class,
  redacted error, attempts, retry time, cost/currency, quarantine, requester, poll
  linkage, and timestamps;
- `tracked_case_provider_snapshots` is append-only application evidence containing
  redacted/safe provider-normalized raw JSON, stable raw and normalized hashes, the
  normalized record, changed-field diff, source boundary, and operation linkage;
- replay creates a new child operation and retains the original failure. A canary
  therefore cannot overwrite incident evidence;
- no existing table, route, or field is removed. Rollback before writer activation
  is the prior exact image; after writes, roll forward is preferred so evidence is
  not discarded. The downgrade is available only when the new tables/columns are
  proven unused.

## Provider execution and health

Scheduled work still uses the dedicated case-tracking poll job, opt-in bookmark
eligibility, per-tenant bounded batches, and the 4 PM–6 PM Asia/Kolkata window.
Every attempted case now creates a durable operation linked to its poll run.
Scheduler invocation, poll run, per-record operation, snapshot/update, notification,
and audit evidence can be followed through the operation/correlation identifiers.

Response outcomes are distinct: `success`, `no_change`, `timeout`,
`authentication`, `rate_limit`, `parse_error`, and a safely serialized unknown
provider-error class. A failed row receives a bounded retry time. A quarantined row
is excluded before the bulk provider request is constructed, so poison data cannot
consume a provider call and does not stop other eligible rows.

`ConnectorHealthProvider.CASE_TRACKING` is now synthesized by the canonical health
service. Enabled tracking with eligible records cannot report healthy without a
recent successful record operation. Latest success/failure/retry/error and
quarantine alerts are tenant-scoped and redacted. Provider operations expose the
same last-good, freshness, response, cost, and correlation facts.

## User workflow and stale-data safety

The Case Tracking page shows provider health, last attempt, last good result, next
scheduled time, freshness, response class, and cost for each bookmark. The control
group is shrinkable, full-width on mobile, and wrapping. Manual refresh remains
rate-limited and audited by the existing SaaS billing service, records the operation
cost, and is disabled when the provider is unavailable or the case is quarantined.
Stale evidence remains visible with manual-docketing guidance; it is not silently
presented as current.

Source documents remain behind the existing CaseOps bearer proxy. Tenant JSON does
not expose provider bearer URLs or credentials. The existing support matrix remains
the only court/jurisdiction availability and pricing owner.

## Replay, quarantine, and incident closure

The existing HMAC replay preview covers record operations with the same tenant,
scope, staleness, tamper, expiry, and 1–25 row bounds delivered in IPLF-002A.
Confirmation uses the existing recent-step-up policy, creates a new pending child,
and does not call the provider in the HTTP request. The next bounded poll executes
the child idempotently.

Ignore on a record-level tracking failure is deliberately implemented as quarantine.
The tracked case and operation are both marked, future bulk calls exclude the case,
and other records continue. Generic “mark resolved” is denied for these incidents.
`resolve-incident` requires:

1. a completed `succeeded` or `no_change` replay child;
2. root-cause text;
3. a prevention/monitoring change;
4. canary evidence; and
5. recent security step-up where the existing MFA or tenant policy requires it.

The closure audit stores only redacted operational text and hashed operation
references.

## Connector credential/disconnect lifecycle

Calendar, Gmail, and Google Drive disconnect routes call
`require_recent_step_up(... purpose="connector_disconnect")` before revocation.
Existing connection services remain the token owner and clear/revoke their stored
token references. The route then refreshes connector health in the same request so
polling/sends cannot continue behind a stale green status. Existing records and audit
evidence are preserved for degraded/manual fallback. A failed security check leaves
the existing connection untouched.

Credential creation/rotation continues to use the existing provider-specific OAuth
callback and platform credential-rotation evidence contracts; no raw secret is
returned by these changes.

## Security and tenant isolation

- all provider-operation reads/actions are `workspace:admin` and company scoped;
- replay preview binds ordered IDs, company, status, update version, cost, and expiry;
- record correlation and source references are redacted in tenant responses;
- provider errors are redacted at persistence and serialization boundaries;
- snapshot metadata removes secret, token, signature, raw-payload, authorization,
  and nested URL-bearing metadata keys before persistence; the top-level source URL
  is retained only in restricted evidence and is never emitted as a tenant bearer URL;
- cross-tenant operation loads return not found;
- source proxy allow-list and bearer injection remain server-side;
- no legal filing, message, provider purchase, destructive delete, or human approval
  was performed.
