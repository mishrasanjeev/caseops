## Implemented controls

### Canonical inventory

`infra/cloudrun/scheduler-inventory.json` is the sole checked-in owner for:

- scheduler name;
- Cloud Run job target;
- cron schedule and time zone;
- dedicated OAuth invoker identity;
- immutable release-digest policy;
- safe-canary classification; and
- legacy schedulers that may be paused only after replacement verification.

The inventory contains exactly six required jobs and rejects duplicate scheduler or job ownership.

### Fail-closed reconciler and drift verifier

`scripts/scheduler_inventory.py` provides three commands:

- `validate` checks inventory schema, uniqueness, immutable-image policy, canary policy, and canonical/legacy separation;
- `reconcile` advances every required job to a supplied `@sha256` image, adds the dedicated identity's job-level Invoker binding, creates or updates the canonical scheduler, verifies all live fields, and only then pauses named legacy schedulers;
- `verify` performs the same live read-only inspection without mutation.

The reconciler preserves each job's command, arguments, environment, secrets, resources, timeout, retries, and runtime service account. It changes only the release image and the scheduler/invoker control plane placed in scope.

### Canonical production release integration

`scripts/deploy-prod.sh` now invokes the reconciler with the resolved immutable API digest. This replaces an incomplete four-job image-only loop. Authority metadata and DB index health can no longer be silently omitted from normal releases.

The established release ordering remains:

1. build API and web images from exact `HEAD`;
2. resolve the API digest;
3. update and execute the migration job;
4. reconcile and verify recurring jobs/schedulers;
5. deploy API and web services;
6. verify exact tags, public health, and the ClamAV sidecar.

### Tenant-safe activity-report logs

`apps/api/src/caseops_api/scripts/send_activity_report.py` no longer serializes the `report` object. Its stdout record is limited to:

- `status`;
- `generated_at`; and
- aggregate `account_count`.

It does not log company names, company IDs, account snapshots, activity metrics, invoice/outstanding values, report HTML/text, recipient payloads, or provider credentials.

### CI and program-control gates

CI now validates both:

- the 436-requirement / 68-journey IP program manifest and generated views; and
- the production scheduler inventory.

The program manifest remains the sole manually maintained status source; generated Markdown views were regenerated after the checkpoint update.

### First exact-commit CI result and repair

The first GitHub CI run for `635d586` passed API Ruff (including both new validators), web typecheck/Vitest/build, Postgres/pgvector validation, Security, and CodeQL. API coverage shard 1 failed during collection before product tests ran:

```text
tests/test_scheduler_inventory.py:8: in <module>
    from scripts import scheduler_inventory
E   ModuleNotFoundError: No module named 'scripts'
```

Root cause: local focused tests were launched from repository root, while CI intentionally launches pytest from `apps/api`; repository-root `scripts` is therefore not importable as a package in CI. The test was corrected to load `scripts/scheduler_inventory.py` through `importlib.util.spec_from_file_location`, the same cwd-independent pattern already used by the IP manifest test. The corrected tests were rerun from `apps/api` and passed 9/9. This was a test-harness import fix only; it did not change runtime scheduler or activity-report behavior.

The next exact-commit CI run proved all four API coverage shards, aggregate per-area coverage, API Ruff/validators, web typecheck/Vitest/build, and Postgres/pgvector. Its Playwright job reported 120 passed, one skipped, and one failed before the failed test's browser actions ran. The failure was a 409 from `/api/bootstrap/company`: the July 28 and July 29 navigation regression files both owned static company slug `legal` and could bootstrap concurrently. The July 28 fixture was isolated with a per-process slug and email. The exact two-spec pair then passed 3/3 locally under `playwright.config.ts`. This is test-data isolation; no product navigation behavior changed.

## Rollback plan

If runtime health or logging regresses:

1. deploy the prior API/web images from commit `cadb46d`;
2. pin the six jobs to the prior known digest only if application rollback requires it;
3. retain additive IAM bindings unless they are the identified fault;
4. inspect health and ClamAV presence before restoring traffic.

If scheduler cadence/target behavior regresses:

1. pause the affected canonical scheduler;
2. for case tracking only, resume `caseops-case-tracking-poll-midnight` as the preserved compatibility path;
3. do not delete either scheduler until the observation window and rollback period close;
4. run `scheduler_inventory.py verify` and a side-effect-safe canary before re-enabling.

The migration was idempotent at the existing head; no destructive downgrade is required or authorized for this slice.
