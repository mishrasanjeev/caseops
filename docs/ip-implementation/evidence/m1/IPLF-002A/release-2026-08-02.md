## Delivered contract

Connector health now serializes last attempt, last successful/last good, next
scheduled retry, a 24-hour freshness classification, response class, redacted
current error, and operator-attention state. It computes health fail-closed: an
enabled/configured connector cannot be healthy without a recent successful
check. Disabled, blocked, stale, and never-successful states remain distinct.

Provider-operation output now accepts every kind already emitted by its
aggregator (`drive_file_candidate`, `calendar_event_candidate`,
`inbound_email_event`, and `connector_health` were previously rejected by the
schema). Rows expose redacted correlation reference, response class, attempt,
last-good/next-scheduled timestamps, affected-record count where known,
retryability, quarantine state, and cost basis.

Replay is preview-then-confirm:

- preview accepts 1-25 unique tenant-visible operation IDs;
- the signed token binds tenant, ordered scope, status, update version, expiry,
  currency, and estimated cost;
- malformed, cross-tenant, expired, non-replayable, and changed previews fail
  closed;
- confirmation requires an operator reason and the existing MFA step-up when
  enrolled or policy-enforced;
- batch confirmation and audit commit atomically;
- the same confirmed token is idempotent and cannot create another durable row;
- provider calls never occur in the request; existing workers retain ownership;
- dead-letter rows stay quarantined until explicit preview and confirmation.

## Security and privacy

Both read and mutation routes require `workspace:admin`. Operation loading is
company-scoped before any preview or mutation. Tokens are HMAC-SHA256 signed
with the configured authentication secret and expire after five minutes. Raw
operator reasons and unredacted identifiers are not copied into action audit
metadata. Connector errors are redacted during persistence and again during
serialization, covering direct or legacy unsafe writes. No credentials, OAuth
tokens, raw payloads, message bodies, or provider documents are exposed.

## Data, migration, compatibility, and rollback

There is no schema change, migration, backfill, or writer switch. The API change
is additive except that replay confirmation now requires a preview token.
Generated OpenAPI types and the in-repository Zod boundary were updated in the
same release. Ignore and mark-resolved contracts are unchanged.

Rollback is an exact-image rollback. Previously confirmed rows remain safely
`pending` or `queued` under existing idempotency keys and existing workers. No
data contraction or reverse migration is required. The old UI will not issue a
valid replay against the new API, so API and web images must be deployed and
rolled back together.
