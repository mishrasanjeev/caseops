## Contract facts learned while writing these

Two API contracts differ from what the path descriptions imply, and the tests
now encode the real ones:

1. **There is no "finalize the current version" operation.**
   `IpDocketVersionCreateRequest` extends `TrademarkParticularPayload`, so every
   version write must carry the complete particulars. Approval is therefore
   always a resubmission, never a flag on its own.
2. **`FilingManifestItem` requires a stable `key`**, not just a label — so a
   manifest row is addressable across versions.

## Defect found — recorded, not asserted

**`create_ip_docket` auto-finalizes the first particulars version.** It calls
`_new_version(..., finalize=not errors)`, so any docket created with clean
particulars is marked approved at v1 — by manual creation *and* by bulk import.

This is contrary to **TM-DATA-14**:

> The filing preview renders the exact data/form/document/fee/signatory package
> that will be submitted and produces an immutable manifest hash **approved by
> the authorized reviewer**.

An imported record therefore carries an approved filing manifest with **no
authorized reviewer**, and `UJ-54-NORMAL`'s "capture **and approve**" collapses
into a single create call.

I did **not** assert the current behaviour in a test, because locking
auto-approval into a passing test would entrench it. The `UJ-54-EXC-04` test
proves the declaration guarantee — which genuinely holds — and this defect is
reported here for triage.

Related gaps in the same requirement, unaddressed: there is no manifest **hash**,
no fee or signatory package, and no reviewer identity on the approval.
