## Scope delivered

`GET /api/ip/deadlines/{deadline_id}/dependencies`

A read-only provenance graph derived entirely from stored calculation evidence.
Node kinds: `trigger_event`, `rule_version`, `calendar_version`, `extension`,
`predecessor_deadline`, `override`.

Three properties make it trustworthy rather than decorative:

1. **It never recomputes.** The graph reports the inputs that actually produced
   the stored date. A rule disabled after the fact cannot rewrite the
   explanation — the test disables the governing rule and asserts the date,
   trace and citation are unchanged while the rule node honestly reports its
   current `disabled` status.
2. **A missing input is reported, not omitted.** Each node carries `available`,
   and `unavailable_inputs` lists any kind that could not be resolved, so an
   incomplete chain cannot look complete.
3. **Supersession is followed.** Because override supersedes rather than
   mutating in place, the current record links back through
   `superseded_chain`, and the superseded calculation remains independently
   readable with its own original date.

## An untested branch, stated plainly

The `available: false` / `unavailable_inputs` reporting is **defensive and not
covered by a test**. I attempted to exercise it and could not reach it honestly:

- Deleting a rule version violates the `ip_deadlines` foreign key.
- Pointing `supersedes_deadline_id` at another company's deadline violates the
  composite `(supersedes_deadline_id, company_id)` foreign key.

The database prevents exactly the dangling states the branch defends against, so
while FKs hold it is unreachable. I kept the code because a future retention
purge or `SET NULL` path could reach it, but I am not claiming test coverage for
it, and I did not weaken a constraint or fabricate a scenario to manufacture a
passing test.

## Explicit caveats

- **Only the `CAL-OPS-06` dependency-graph facet is delivered**, and the
  requirement itself stays `in_progress` because `IPLF-035B` and `IPLF-039H`
  also own it. All other `CAL-OPS` and `IP-DL` requirements remain open on
  `IPLF-034B`.
- **Local SQLite only.** No real-PostgreSQL CI, no query-plan evidence, no
  deployment, no production verification.
- **No frontend, no E2E.** `IP-DL-03` requires the UI to explain the calculation
  in plain language and link to the governing verified source; this slice
  supplies the backend contract only and does not close it.
- **Extensions are read from stored calculation inputs**, not from an
  extension/order record. The PRD's "extension/order" node is therefore only as
  rich as `extension_days`; a first-class extension order is not modelled.
- **No graph for hearings, internal targets or reminders** — only legal
  deadlines in `ip_deadlines`.
- Fixtures are synthetic; no real client, matter, registry or lawyer-approved
  legal rule.
