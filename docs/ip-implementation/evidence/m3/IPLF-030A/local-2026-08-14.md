## Why this slice needed a coverage allocation first

Every M3 `A` (foundation) slice shipped from Phase 0 with **zero requirement and
zero journey-path coverage**, while the paired `B` slice carried all of it. The
manifest validator rejects an implemented slice with empty coverage, so no M3
`A` slice could ever be closed and the whole M3 chain was structurally blocked.

This slice fixes that for `IPLF-030` by moving the subset it genuinely
implements onto `IPLF-030A` and leaving the rest on `IPLF-030B`. The same
pattern is still required for `IPLF-031A`, `032A`, `033A`, `034A`, `035A`,
`036A`, `037A`, `038A` and `039G`.

## Scope delivered

A read-only, cursor-paginated portfolio query at `GET /api/ip/portfolio`.

- **IP-PORT-05.** A row is one *jurisdiction/application* record joined to the
  mark it belongs to. One mark filed in two offices yields two rows sharing one
  `asset_id`, and the application identity is never collapsed into the mark.
- **IP-PORT-02.** Server-owned filters: free-text (mark / docket title /
  primary identifier), matter, asset kind, jurisdiction, office, filing phase,
  docket status, and an explicit `include_inactive`. Filters compose, normalize
  case server-side, and an unknown value narrows to zero rather than falling
  open.
- **UJ-04-EXC-02.** Access is delegated to the canonical
  `visible_ip_dockets_filter` policy plus the existing non-operational-Matter
  rule. A restricted record contributes **no row, no count, no title and no
  id**, and a targeted search for it cannot confirm it exists.
- Per-row data-quality signals: `record_complete` with typed
  `incomplete_reasons`, and open / unconfirmed / overdue legal-deadline counts
  read from the existing `ip_deadlines` evidence.

## Ownership and duplicate-work analysis

Classification: **EXTEND** (read-only projection). No new table, migration, or
writer.

- No second portfolio store. Rows are assembled from the existing
  `TrademarkApplication`, `IpAsset`, `IpDocketRecord` and `IpDeadline` owners.
- No second access policy. `visible_ip_dockets_filter` stays the single
  fail-closed internal owner; this slice does not re-derive visibility.
- No second deadline owner. Counts are read from `ip_deadlines`; nothing is
  written and no operational deadline is projected.
- `registry_sync_state` is reported as the literal `"unavailable"` rather than
  a fabricated zero, because IP-office synchronisation is M5 (`IPLF-050/051`).

## Defect found while building this

`GET /api/ip/portfolio` originally compared the decoded cursor timestamp as a
**string** against a `DateTime` column. On SQLite that silently fails to filter,
so page two returned page one's rows. Caught by the pagination test and fixed by
parsing the cursor back into a `datetime`. A string cursor would have produced
duplicate rows across pages in production.

## Explicit caveats

- **Local SQLite only.** No real-PostgreSQL CI, no query-plan or index
  verification at representative tenant volume (`ARCH-OPS-11` is untouched), no
  deployment, no production verification.
- **No frontend.** There is no portfolio UI, no desktop or narrow-mobile
  evidence, and no E2E. The generated client types exist but nothing consumes
  them.
- **List only.** No grid view, saved views, configurable columns, bulk actions,
  import, or export — all `IPLF-030B`.
- **`IP-PORT-10` is not closed.** Complete/incomplete/unconfirmed/overdue counts
  are real, but "sync failures" cannot be reported until M5 supplies registry
  synchronisation, so the requirement stays co-owned and open.
- **Counts are page-scoped, not scope-wide.** `counts.total` describes the rows
  returned for the current page, not the full filtered result set. A scope-wide
  aggregate is `IPLF-030B` work.
- Fixtures are synthetic; no real client, mark, proprietor, or registry data.
