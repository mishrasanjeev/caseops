# IPLF-031A — duplicate identifier reconciliation (IP-ID-07, UJ-05)

**Slice:** `IPLF-031A` (M3; repository-implemented, locally verified, **not released**)
**Date:** 2026-08-14
**Program status:** `PROGRAM INCOMPLETE`

## The dead-end this closes

Duplicate **detection** already existed from `IPLF-021`: a colliding identifier
is stored with `reconciliation_status="needs_review"` and the creating call
returns `duplicate_candidates`. Separately, `IP-ID-04` refuses to let a filing
enter `filed` phase without a **confirmed** current application number.

Nothing in the product could move an identifier out of `needs_review`. A
genuine duplicate therefore left the record permanently unable to reach `filed`
phase, with no operator path to resolve it. That is a workflow dead-end in
shipped code, not merely a missing feature.

## Scope delivered

Two additive routes on the existing docket/identifier owner:

- `GET /api/ip/dockets/{docket_id}/identifiers/{identifier_id}/duplicates` —
  a preview listing the competing identifiers with a decision token, whether an
  automatic merge is blocked, the typed blocking reasons, and the decisions
  actually allowed. It changes nothing.
- `POST /api/ip/dockets/{docket_id}/identifiers/{identifier_id}/reconcile` —
  resolves by explicit decision:
  - `distinct` — the identifier is legitimately separate; status becomes
    `confirmed` and the reason is recorded, unblocking `filed` phase.
  - `supersede` — the identifier retires in favour of a named survivor from the
    preview: `effective_until` is set, `supersedes_identifier_id` links the
    survivor, `is_primary` clears, and the raw value stays in history.

**IP-ID-07 is honoured literally: nothing ever merges silently.** A resolution
requires a current preview token, an explicit decision, and a reason ≥ 5 chars.
Both outcomes are audited as `ip.identifier.duplicate_resolved` with the
decision, reason, token, candidates, and any blocking reasons.

### UJ-05-EXC-01 — when automatic merge is refused

`supersede` is withheld and only `distinct` remains available when any of these
hold across the identifier and its candidates:

| Reason | Meaning |
|---|---|
| `conflicting_terminal_state` | a record is closed, abandoned, refused, withdrawn or registered |
| `different_client_matter` | the records belong to different client matters |
| `privileged_permission_mismatch` | one record is restricted and another is not |
| `inactive_record` | a record is inactive |

A blocked merge is not a failure — it means the decision belongs to a human
owner. The typed 409 carries `ip_duplicate_merge_blocked` and the reasons.

## Ownership and duplicate-work analysis

Classification: **EXTEND**. No new table, migration, or writer.

- `IpIdentifier` remains the sole identifier owner; this adds commands over the
  existing `reconciliation_status`, `effective_until`,
  `supersedes_identifier_id` and `correction_reason` columns rather than a new
  reconciliation store.
- No second access policy: the preview reuses the existing docket access check,
  so a competing record the caller cannot open never appears as a candidate.
- No second audit trail: resolution records through `record_from_context`.

## Explicit caveats

- **Local SQLite only.** No real-PostgreSQL CI, no concurrency proof for the
  `with_for_update()` reconciliation path, no deployment, no production
  verification.
- **No frontend.** There is no reconciliation UI, no desktop or narrow-mobile
  evidence, and no E2E. Generated client types exist but nothing consumes them.
- **`supersede` retires the duplicate; it does not merge record content.** No
  documents, deadlines, events, or proceedings move between dockets. Whether a
  true record merge is required is `IPLF-031B` scope and is not implemented.
- **`IP-ID-01..06` and `IP-ID-08` stay co-owned and open.** This slice closes
  `IP-ID-07` and the two UJ-05 paths only; the identifier foundation itself
  came from `IPLF-021`.
- Terminal-state detection uses docket status strings; there is no separate
  legal terminal-state registry, so a new terminal status added elsewhere would
  need adding to `TERMINAL_DOCKET_STATES`.
- Fixtures are synthetic; no real client, mark, proprietor, or registry data.
