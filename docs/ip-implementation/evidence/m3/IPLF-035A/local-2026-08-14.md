# IPLF-035A — deadline notification-intent preview and status (NOTIF, UJ-10)

**Slice:** `IPLF-035A` (M3; repository-implemented, locally verified, **not released**)
**Date:** 2026-08-14
**Program status:** `PROGRAM INCOMPLETE`

## What remained

`IPLF-025A/025B` and the notification convergence work already deliver the
shared hearing, next-hearing, calendar and reminder owners, the delivery
dispatcher with leases, suppression, fallback and recovery, and the admin
notification surfaces. `confirm_deadline` already enqueues reminder intents.

What did not exist was the **preview**: a user confirming a critical legal
deadline had no way to see which reminders would be created, for whom, when, or
whether a named owner would actually receive them. The delivery plan only became
visible after it had already been committed.

## Scope delivered

| Route | Behaviour |
|---|---|
| `POST /api/ip/deadlines/{id}/notification-preview` | The reminder plan confirmation would enqueue. Writes nothing. |
| `GET /api/ip/deadlines/{id}/notifications` | The intents that exist for this deadline and their delivery state. |

Two properties matter:

1. **The preview cannot drift from dispatch.** It mirrors `confirm_deadline`'s
   schedule exactly — 09:00 in the deadline's own timezone, `offset` days before
   the result date — and it reuses the dispatcher's own `_recipient_context`
   helper for the access check rather than reimplementing eligibility. The test
   confirms the deadline afterwards and asserts the created intents' scheduled
   times are **the same set** the plan promised.
2. **Ineligible recipients are shown, not dropped.** Each entry carries
   `would_deliver` and a typed `withheld_reason`
   (`membership_not_found`, `membership_inactive`,
   `responsibility_not_acknowledged`, `recipient_lost_access`). A named owner who
   would silently receive nothing is visible **before** anyone relies on the
   reminder, which is the point of `UJ-10-EXC-03`.

Offsets are de-duplicated, sorted, and negative values discarded; no offsets
means no plan rather than an implicit default. Previewing is proved to create
zero intents.

## A contract inconsistency found and fixed

The first test run showed the preview emitting aware UTC (`...T03:30:00Z`) while
status emitted naive (`...T03:30:00`) for the **same instant**.
`NotificationDeliveryIntent.scheduled_for` is a `DateTime(timezone=True)` column
that round-trips naive on SQLite. Rather than relax the assertion, the status
serializer now normalizes through `_utc()`, so both surfaces emit the same shape
and the API contract does not leak backend timezone behaviour.

## Explicit caveats

- **Only the preview/status facet is delivered.** All 14 `CAL-OPS` and 24
  `NOTIF` requirements on `IPLF-035` remain co-owned and open on `IPLF-035B`;
  none is claimed closed here.
- **In-app only.** No email, SMS, or external channel is planned or dispatched,
  and `external_delivery_enabled` is a literal `False` in the contract.
- **The preview does not check suppression or user notification preferences.**
  A recipient who is access-eligible but has suppressed or muted this event type
  will show as `would_deliver: true` and may still receive nothing. That is a
  real gap between the plan and reality, and it is not covered.
- **Hearings are not covered.** `UJ-10` also spans hearing scheduling and
  reschedule supersession (`EXC-01`, `EXC-02`); this slice covers the deadline
  reminder plan only.
- **No `UJ-62` external calendar sync** — provider outage, revocation, external
  edits, ethical-wall redaction and the timezone/date-only rule are untouched.
- **Local SQLite only.** No real-PostgreSQL CI, no delivery-worker run, no
  in-app render, no frontend, no E2E, no deployment.
- Fixtures are synthetic; no real client, recipient, or external provider.
