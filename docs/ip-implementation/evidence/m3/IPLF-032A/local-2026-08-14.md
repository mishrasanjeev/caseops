# IPLF-032A — neutral bulk import owner and typed IP staging (UJ-02)

**Slice:** `IPLF-032A` (M3; repository-implemented, locally verified, **not released**)
**Date:** 2026-08-14
**Program status:** `PROGRAM INCOMPLETE`

## Ownership decision — the constraint this slice is really about

`ARCH-OPS-23` and the master prompt forbid an `ip_import_jobs` table and forbid
reusing Matter row-commit logic as generic orchestration. This slice therefore
introduces:

- **`bulk_import_jobs`** — a *neutral*, domain-tagged import owner. The domain
  is a checked enum (`ip_trademark` today), so a future domain extends the enum
  rather than cloning the table.
- **`ip_import_rows`** — the typed IP staging rows for one job.

The legacy `matter_bulk_import_jobs` and `employee_bulk_import_jobs` owners are
**untouched and remain canonical** for their own domains. Nothing is migrated
out of them and no adapter rewrites them. The migration test asserts both
legacy tables survive the expand *and* the rollback, and that `ip_import_jobs`
does not exist.

Commit materialises records through the existing **`create_ip_docket`** writer
rather than inserting docket rows directly, so docket validation, access
seeding, versioning and audit stay with their canonical owner.

## Scope delivered

| Route | Behaviour |
|---|---|
| `POST /api/ip/imports` | Stage + validate rows. Writes nothing to the portfolio. |
| `GET /api/ip/imports/{job_id}` | Preview with an `preview_expired` flag. |
| `POST /api/ip/imports/{job_id}/revalidate` | Refresh an expired preview against current data. |
| `POST /api/ip/imports/{job_id}/commit` | Idempotent commit through the canonical writer. |

### UJ-02 path coverage

| Path | How it is satisfied |
|---|---|
| `NORMAL` | Stage → preview → commit; dockets appear through `GET /api/ip/dockets`. Staging is proved to write nothing. |
| `EXC-01` | An expired preview returns `preview_expired`, commit is refused with `ip_import_preview_expired`, and the superseded token cannot be replayed after revalidation. |
| `EXC-02` | Each row's outcome is persisted immediately, so a row that becomes uncommittable fails alone; siblings commit and the job ends `committed_with_errors`. |
| `EXC-03` | Replay with the same `idempotency_key` returns the original terminal result with `replayed: true` and creates no second record; a *different* key is refused rather than re-executing. |
| `EXC-04` | A foreign-tenant `matter_id` and a nonexistent id produce the **identical** `unknown_reference` error; the response is asserted to contain no foreign company name or matter code. |

Invalid rows are reported with typed field/code errors and marked `skipped` on
commit — never silently dropped. Formula-injection protection prefixes leading
`= + - @` so a re-exported cell is inert in Excel/Sheets.

## Two ownership gates caught this slice

1. The `IPLF-028C` data-governance inventory gate rejected both new tables until
   they were registered in `DATA_GOVERNANCE_MAP.yaml`.
2. The `IPLF-019A` ownership ledger rejected the service because its **docstring**
   contained the forbidden identifier for an IP-specific job table. The scan is a
   literal token match over `apps/api/src`, and it was right to fire: the rule is
   that the token must not appear in source at all. The docstring was reworded to
   state the constraint without naming the forbidden identifier. The gate was not
   weakened and no allowlist entry was added. The migration test still asserts
   the table does not exist, because tests are outside the scanned tree.

## Design note found during implementation

`create_ip_docket` commits internally, so a per-row `SAVEPOINT` could not wrap
it — the nested transaction closed underneath the context manager. Row outcomes
are therefore persisted immediately per row, which is what actually makes
`EXC-02` correct: an earlier attempt kept outcomes in memory until the end, and
a later row's rollback silently discarded an already-successful sibling's
`committed` status. The test caught it.

## Explicit caveats

- **Local SQLite only.** No real-PostgreSQL CI, no concurrency proof for the
  `with_for_update()` job path, no deployment, no production verification.
- **No file parsing.** The API accepts already-parsed JSON rows. There is **no
  CSV/XLSX upload, no encoding/delimiter handling, and no template download**;
  `IP-PORT-08` explicitly stays open on `IPLF-030B`.
- **No frontend, no E2E.** Generated client types exist but nothing consumes them.
- **No duplicate suggestions.** `IP-PORT-08` also requires duplicate suggestion
  and reconciliation at import time; this slice does not detect duplicates
  across the staged set or against existing records.
- **No cancel, retry, or history listing** — a single job is readable by id only.
- **Commit is synchronous and bounded to 1000 rows.** It is not a background
  job, so a large import would block the request; `UJ-04-EXC-03`-style
  background execution is not implemented.
- **Rows are capped at 1000** by the request schema; larger portfolios are not
  supported yet.
- Fixtures are synthetic; no real client, mark, proprietor, or registry data.
