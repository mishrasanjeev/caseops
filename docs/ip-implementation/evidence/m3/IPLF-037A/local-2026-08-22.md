## Scope delivered

This slice implements the two records assigned to `M2M3-IPLF-037` in the
authoritative ownership ledger:

- `ip_renewal_terms` owns renewal/grace/instruction/filing/acceptance/next-term
  legal state.
- `ip_client_instructions` owns attributable, versioned instruction scope,
  authority, acknowledgement, supersession, and resulting-act evidence.

The additive API contract provides:

| Route | Contract |
|---|---|
| `GET /api/ip/renewals/foundation-contract` | Names every canonical owner and the fail-closed completion rule. |
| `GET/POST /api/ip/dockets/{docket_id}/renewal-terms` | Tenant/access-scoped list and creation from confirmed registration/deadline evidence. |
| `POST .../{term_id}/instructions` | Creates an initial instruction or a stale-write-fenced superseding revision. |
| `POST .../{term_id}/instructions/{instruction_id}/acknowledge` | Accepts, rejects, or requests clarification with actor/time/reason evidence. |
| `POST .../{term_id}/transition` | Applies an evidence-gated, optimistic-concurrency renewal transition. |

## Fail-closed state contract

- Term creation requires a confirmed `registration` event, confirmed `renewal`
  deadline, and, when present, a confirmed `renewal_grace` deadline from the
  same tenant and docket.
- Instruction revisions require the current instruction id and row version;
  acknowledgement requires expected status, row version, and update timestamp.
- Term transitions require expected state, version, and update timestamp.
- `filing_in_progress` records initiation only. It cannot set acceptance or
  completion.
- `filed` requires a confirmed filing event. `accepted` additionally requires a
  confirmed registry-acceptance event.
- `completed` additionally requires an accepted current certificate linked to
  the docket and a confirmed next renewal deadline triggered by that exact
  acceptance event.
- Recorded fee, filing, acceptance, certificate, and next-term references are
  immutable through this command path; corrections must use their canonical
  legal-event/document owners.
- Database constraints independently prevent filed/accepted/completed rows from
  omitting the corresponding evidence.

## Data and migration boundary

Migration `20260822_0002` creates only the two empty tables and their
tenant-leading indexes. It rewrites no existing row and downgrades cleanly to
`20260822_0001`. Composite tenant foreign keys are used wherever the referenced
owner exposes `(id, company_id)`; service filtering also applies on every read
and write. The fee and communication owners expose only a single-column primary
key, so the service performs the tenant/docket check before storing those links.

Both tables are registered as `tenant_restricted_legal_content` with the
existing `registry_fail_closed` disposition handler. No retention, export,
purge, restore, notification, billing, or provider operation is activated.
The generated runtime data-class projection was rendered from the same ORM
inventory and validates against the committed governance map.
