## Existing Work Reused

The implementation audit found that IPLF-023A/023B already owned the legal
deadline engine, versioned rules and working calendars, proposal, confirmation,
coverage, reminders, recalculation, override, completion, exception queue, and
operational projection. IPLF-025B already owned shared calendar/reminder
transport. IPLF-034A already supplied the read-only dependency graph.

IPLF-034B therefore adds no table, migration, legal-date calculator, extension
writer, reminder dispatcher, calendar event owner, or duplicate task/deadline
writer. It closes the remaining user and release-proof gaps over those owners.

## Delivered Scope

- The IP deadline workspace opens verified HTTP rule and calendar sources and
  lazily renders the IPLF-034A stored dependency graph, engine/source versions,
  unavailable inputs, overrides, and predecessor evidence.
- Conflicting inputs fail closed. Confirmation requires a corrected date,
  reason, evidence reference, responsible lawyer, and critical-deadline backup.
  Resolving a date-less provisional record retains the original uncertainty in
  its trace; correcting an existing dated record continues to create a
  successor.
- Filing an extension application does not move the legal date. Only an
  activated source-versioned rule/calendar input or the existing evidenced
  override command may do so. This is an explicit no-schema/no-second-writer
  decision.
- The shared calendar retains its compatible hearing/task/deadline transport
  contract while adding semantic display types for legal filing deadlines,
  internal targets, hearings/listings, renewals, client-instruction dates,
  reminders, tasks, and other deadlines.
- IP-backed legal deadlines and internal targets deep-link to their docket.
- Deadline mutations are serialized in the UI to prevent overlapping legal
  actions.
- The product guide, law-firm page, and governed deadline workflow document now
  describe the delivered behavior without claiming deployment or legal review.
