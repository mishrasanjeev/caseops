# IPLF-039C rebuild — increment 1: signed-off daily docket control review

**Slice:** `IPLF-039C`
**Date:** 2026-08-15
**Scope of this increment:** `CAL-OPS-09` and `CAL-OPS-13`, covering `UJ-59`
(4 paths) and `UJ-50-EXC-01`.

## Why a rebuild

The 2026-08-15 inspection audit found this slice largely unbuilt — roughly 4 of
22 paths — while recorded `implemented / passed / deployment_verified`. Most
notably `UJ-59` requires the daily docket control report to be *produced **and
signed off***, and **no sign-off step existed at all**. Patching around that was
not possible; the review had to become a real record.

## What this increment adds

A durable `ip_docket_control_reviews` record, so a report becomes reviewable
evidence rather than a transient projection.

| Behaviour | How |
|---|---|
| Generation time, filters and freshness visible (`CAL-OPS-09`) | The review stores `generated_at`, the exact `filters` used, and a `freshness` block naming stale sources and failed queries. |
| Sign-off | `POST /control-reviews/{id}/sign-off` records signer identity, label snapshot and timestamp, fenced on `expected_version` and terminal once signed. |
| Incomplete review cannot be signed (`UJ-59-EXC-01`) | Any stale source or failed query sets `completeness_status="incomplete"` with typed reasons; sign-off returns `ip_control_review_incomplete`. |
| Export failure blocks completion (`UJ-59-EXC-03`) | A recorded `failed` export returns `ip_control_review_export_failed` on sign-off; a successful regeneration clears it. |
| Restricted work leaks nothing (`UJ-59-EXC-02`, `UJ-50-EXC-01`) | Counts and exceptions derive from the access-filtered listing, so an unauthorised reviewer's report counts only what they may open and the restricted id and title appear nowhere. |
| Exceptions cannot be hidden (`CAL-OPS-13`) | Mandatory exceptions are computed at generation and **stored on the review**. A filter that plainly excludes a record still reports its exception, re-reading cannot drop it, and signing off does not clear it. |

The manifest hash covers generation time, filters, counts, exceptions and
incompleteness reasons, and is proved stable across sign-off — the artefact
signed is the artefact produced.

## Database-level enforcement

The service rules are duplicated as check constraints so the state is
unreachable even outside the service:

```sql
signed_off_at IS NULL OR (completeness_status = 'complete' AND export_status <> 'failed')
signed_off_at IS NULL OR signed_off_by_membership_id IS NOT NULL
```

## Ownership

Classification: **NEW** record, **EXTEND** of the existing report.
`ip_docket_control_report` and `list_ip_dockets` remain the canonical
projections; the review stores their output plus review state and creates no
second docket, coverage or deadline owner. Access is inherited from
`list_ip_dockets`, so no second access path exists.

## Increment 3 — the reassignment workflow (UJ-57, remaining 5 paths)

CAL-OPS-08 requires an atomic preview **and** an accepted replacement or
approved emergency coverage. Reassignment previously moved ownership
immediately, so critical work could be handed to someone who never accepted it.

Migration `20260815_0002` adds `pending_replacement_membership_id`,
`replacement_decision`, `replacement_decided_at`, `replacement_decision_reason`,
`emergency_until` and `emergency_escalation_membership_id` to

so current ownership is preserved exactly.

| Path | Proven behaviour |
|---|---|
| `UJ-57-NORMAL` | Preview returns the affected coverage and docket ids, an access verdict, and a 64-character token. Proposing marks the row `pending` and **leaves the current owner in place**; only the replacement's acceptance moves ownership, and exactly one coverage row exists throughout. |
| `UJ-57-EXC-03` | A rejection returns the work to the original owner — never unowned — records the reason, is terminal against replay, and only the **named** replacement may decide (403 otherwise). |
| `UJ-57-EXC-04` | Adding another coverage after the preview invalidates the token; the proposal is refused with `ip_coverage_preview_stale` and neither row is touched. A fresh preview covering both rows succeeds. |
| `UJ-57-EXC-05` | Emergency cover transfers immediately but is refused without an escalation owner and refused if the expiry is already past. When granted it records `emergency_until`, the escalation owner, and status `emergency`. |
| `UJ-57-EXC-06` | Every pre-existing audit row is byte-identical after the transfer: history is appended, never rewritten. The acceptance is attributed to the replacement and is proved not to be backdated to the original owner. |

Two rules are enforced in the database as well as the service: a `pending`
transfer must name who it waits on, and emergency cover must carry an escalation
owner.

### Semantic change worth noting

`reassign-propose` no longer transfers ownership. The pre-existing
`bulk-reassign` route still transfers immediately, so the two now differ. That
is deliberate for this increment — bulk-reassign retains its access guard from
the earlier fix — but the routes should be reconciled before release so there is
one transfer semantic, not two.

# Increment 5 — one transfer semantics, not two (`CAL-OPS-08`)

**Date:** 2026-08-15
**Scope:** reconciling `bulk-reassign` and single reassignment with the
propose/accept workflow added in increment 3.

## What auditing found before writing code

Increment 3 added a propose/accept transfer. It did not remove the two paths
that already moved responsibility, so the product had **three** ways to change
who owns a filing date and they disagreed:

| Path | Behaviour before |
|---|---|
| `reassign_ip_deadline_coverage` | moved responsibility at once, wrote `accepted_at = _now()` |
| `bulk_reassign_ip_deadline_coverages` | same, across the whole portfolio |
| `propose_ip_coverage_reassignment` | marked pending, waited for the named replacement |

The first two wrote `accepted_at` **with no human act**. That field is the
record that a named person took responsibility for a deadline — the artefact
you would produce to show who owned a date that was missed. Writing it when
nobody accepted is a false record, and `CAL-OPS-08` requires an *accepted*
replacement, which both paths bypassed entirely.

This was not in the original increment-5 plan, which described the work as
reconciling `bulk-reassign` alone. Reconciling only the bulk path would have
left the identical falsehood on the single path, so the scope was widened to
both.

## The reconciliation

One rule, applied to every path: **only `decide_ip_coverage_replacement` — which
runs on the replacement's own action — may write `accepted_at`.**

- **`proposed` (the new default).** Responsibility does not move. The row goes
  to `transfer_pending` with the replacement named, and the current owner keeps
  the date until the replacement accepts. This is the routine case.
- **`immediate`.** Exists only for departure and emergency, where the outgoing
  person cannot be waited on. Responsibility moves now, but the row is recorded
  as **awaiting acknowledgement**, never as accepted, and an escalation owner is
  mandatory.

Two consequences worth stating:

- **A proposal is not projected onto the replacement's calendar.** Work someone
  has not accepted must not appear as their commitment, so the `CalendarEventSync`
  row is only created once responsibility is actually theirs.
- **Declining an immediate transfer escalates.** The work has already moved, so
  a decline cannot simply be refused in place, and it must not go back to
  someone who has left. It goes to the named escalation owner and the row
  becomes `escalated`. If no escalation owner exists the decline is refused
  (`ip_coverage_no_escalation_owner`) rather than leaving the deadline unowned.
- **Naming a backup stays immediate.** A backup is not the accountable party
  until responsibility actually moves to them, so backup assignment does not
  require acceptance. The access guard from the earlier fix still covers both.

Employee offboarding is the one caller that passes `immediate`; the admin
running the offboarding is the escalation owner.

# Increment 6 — the accept/decline surface (`CAL-OPS-08`)

**Date:** 2026-08-15
**Scope:** closing increment 5's own blocker — a replacement could only act on a
proposed transfer through the API.

Design context was taken from `.impeccable.md` and
`.claude/skills/impeccable/SKILL.md`, as `CLAUDE.md` requires. The skill's
`post-update-cleanup` step was **not** run: it deletes files and rewrites the
vendored skill, which is unrelated to this task.

## The read path came first

Increment 5 left proposals discoverable only by opening each docket. That is the
wrong shape: a proposal is addressed to **one person**, and leave cover is
offered across a portfolio, so the reader would have had to open forty records
to discover they had been offered anything.

`GET /api/ip/deadline-coverages/awaiting-me` lists the transfers waiting on the
caller, carrying what a lawyer needs to answer *"can I hold this date?"* —
record, identifier, deadline, due date, days remaining, criticality, who asked
and why — without opening anything.

**Access is re-checked at read time.** The propose path already refuses a
replacement who cannot open the record, but a grant can be withdrawn afterwards.
A pending decision must not become a standing disclosure of a record the reader
may no longer see, so the listing filters through `can_access_ip_docket` and the
refusal discloses no title.

## Accepting no longer requires prose

The decision endpoint required a five-character reason for **both** outcomes.
Forcing someone to type something in order to accept produces `"ok"` in an audit
trail, which is worse than recording nothing: it looks like a considered reason
and is not.

`reason` is now optional, and required only when declining — declining sends
work back or escalates it, so it must be explained; accepting is self-evidencing
because who acted and when is already recorded. An acceptance given without a
note also no longer erases the proposer's stated reason, which shares the field.

## The surface

A band above the portfolio, because a pending decision blocks someone else's
work. It is **omitted entirely when empty** rather than rendered as an empty
state — an always-present band trains people to ignore the space.

| Decision | Reasoning |
|---|---|
| Sorted soonest-due first | The decision that can still be acted on matters most. |
| The two kinds read differently | A proposal says *"X remains responsible until you accept."* An immediate transfer says *"You already hold this. Declining moves it to Y."* Presenting them identically would misstate what declining does. |
| Decline expands inline | The skill treats modals as lazy; the reason field is progressive disclosure on the row, and *Confirm decline* stays disabled until the reason is real. |
| Criticality is a labelled badge | Never colour alone (WCAG 2.1 AA). Dates use tabular figures per the type direction. |
| No side-stripe accent | `absolute_bans` BAN 1. Rows use a full border. |

# Increment 7 — saved queues and bulk acknowledgement (`CAL-OPS-09`)

**Date:** 2026-08-15
**Scope:** the last two clauses of `CAL-OPS-09`.

The requirement reads: *"Daily docket supports saved team queues,
workload/capacity indicators, bulk acknowledgement/assignment with per-record
validation, and a print/export manifest whose generation time, filters, and
freshness are visible."* Increments 1 and 2 delivered the indicators and the
manifest. This closes the other two.

## Bulk *assignment* is not a new mechanism

Assignment is the transfer path reconciled in increment 5. Building a second
bulk-assign here would have recreated the exact duplication increment 5 removed.
The two are deliberately asymmetric:

| | Boundary? | Behaviour |
|---|---|---|
| Bulk **assignment** | Yes — handing a restricted record to the wrong person | Fails closed for the whole batch |
| Bulk **acknowledgement** | No — a caller can only acknowledge their own work | Validates per record, applies partially, reports every id |

Failing all fifty acknowledgements because one row moved would be worse than
reporting that one. Every requested id is answered for, so a dropped row can
never be mistaken for an acknowledged one.

Four rejection reasons are distinguished: `not_found`, `not_responsible`,
`version_conflict`, `already_acknowledged`, plus `transfer_pending` — an
outstanding transfer is a *decision*, and acknowledging around it would bury the
choice a colleague is waiting on.

A record the caller cannot open is reported as `not_found`, never as one they
may not touch: the second answer would confirm it exists.

## The increment-5 invariant was widened, not relaxed

Increment 5 established that only `decide_ip_coverage_replacement` could write
`accepted_at`, because the transfer paths were recording acceptances nobody
gave. Bulk acknowledgement legitimately writes one — it is the responsible
member taking on their own work.

Rather than adding a name to an allowlist, the rule was **restated**: a function
may write `accepted_at` only if it also gates on `context.membership.id`, i.e.
it acts on the caller's own record. A future transfer path that stamps
`accepted_at` for somebody else still fails the test. The AST check now asserts
both the writer set and that every writer is gated.

## Saved queues

`ip_docket_queues` holds a named, reusable set of daily-docket filters. Scope is
explicit and enforced in the schema, not only the service: a queue is either
shared with a team or personal to the member who saved it, never neither
(`ck_ip_docket_queue_has_scope`). There is no company-wide tier — a queue
everyone can edit is a queue nobody owns.

Saving a team queue requires membership of that team: sharing a view into a
team's workload is a disclosure, not a preference. Another member's personal
queue is invisible, and deleting it is refused as **absent** rather than
forbidden, which would confirm it exists.

# Increment 8 — the daily-docket web surface (`CAL-OPS-09`, `CAL-OPS-13`)

**Date:** 2026-08-15
**Scope:** closing increment 7's finding — the entire daily docket was API-only.

Design context from `.impeccable.md` and the vendored `impeccable` skill, as
`CLAUDE.md` requires. The skill's `post-update-cleanup` step was again not run:
it deletes files and rewrites the vendored skill.

## A missing read path blocked the UI

The daily docket returned aggregate counts per member and escalation ids. It did
**not** return the caller's own deadlines, so a member could be told "seven
unacknowledged" with nothing on screen to acknowledge. A count you cannot act on
is not a feature.

`GET /api/ip/deadline-coverages/mine` returns the caller's coverage with the
record, identifier, deadline, due date, days remaining, criticality, whether it
is acknowledged, and whether a transfer decision is outstanding. Access-filtered
exactly as the counts are, so the list and the count agree — which is asserted
directly (`IPLF-CAL-OPS-09-ACK-05`).

## The rule this surface exists to not break

`UJ-50-EXC-03`: when a source is stale the API returns `null`, not `0`, because
unknown work is not no work. A UI that renders `null` as `0` — or as a dash —
silently undoes the guarantee the backend went to trouble to make. So the count
renders the word **Unknown**, the provenance strip names the stale sources, and
a test asserts that no `0` appears in a stale row.

`CAL-OPS-09` also requires generation time, filters and freshness to be visible.
They are stated in one line at the top rather than hidden behind a tooltip: a
number whose provenance is unknown is not evidence.

## Capability gates were wrong on first write

I gated sign-off on `ip:review`. The API requires `ip:approve`. A reviewer
without `ip:approve` would have been shown a Sign off button that 403s — the
"UI invites failure" pattern the bug protocol names explicitly.

Corrected and then **pinned by a test**: the daily docket needs `ip:read`,
acknowledgement and queues need `ip:write`, sign-off needs `ip:approve`. A
read-only member sees the capacity table and can generate a review, and sees
neither the acknowledgement card, the queue controls, nor a sign-off button.

## The surface

| Section | Behaviour |
|---|---|
| Provenance | Generation time, filters, freshness in one line; stale sources named |
| Workload and capacity | Dense table, tabular figures, availability as a labelled badge — never colour alone |
| Escalations | Reason in words; states whether a backup exists to fall back to |
| Your unacknowledged deadlines | Select and acknowledge in bulk; soonest due first; every rejected row listed with its reason |
| Saved queues | Save the current filters, apply, delete; team vs personal shown as a label |
| Control review | Generate, see completeness and exceptions and the manifest hash, sign off with an attestation |

Two details worth naming. A deadline with an outstanding transfer is **not
selectable** and says why — acknowledging around a pending decision would bury a
choice a colleague is waiting on, and the API refuses it anyway, so the UI must
not offer it. And rejected acknowledgements are listed individually rather than
summarised as a count, because a row that did not acknowledge must never look
like one that did.

Sign-off requires an attestation, unlike acceptance in increment 6. The
difference is real: accepting is self-evidencing because the act is the record,
whereas the attestation *is* the substance of a sign-off.

# Increment 9 — the control-review export control (`CAL-OPS-09`)

**Date:** 2026-08-15
**Scope:** the print/export half of `CAL-OPS-09`, which increment 8 left API-only.

## What auditing found, and why a plain button would have been a lie

`POST /control-reviews/{id}/export` **records an outcome**. It does not produce
an artifact: it writes `export_status` and, on failure, a redacted reason.

So a button that posted `outcome: "generated"` would have recorded a successful
export that never happened — the same falsehood as the fabricated `accepted_at`
in increment 5, in a new place. Worse here, because a recorded `generated` is
what unblocks sign-off: the signature would then rest on an export nobody
produced.

The artifact therefore had to be built.

## The manifest

`buildControlReviewManifest` produces a self-contained printable HTML document
carrying exactly what `CAL-OPS-09` requires be visible — generation time,
filters, freshness — plus completeness and its reasons, the report counts, every
mandatory exception (`CAL-OPS-13`), and the `manifest_sha256` so a filed copy can
be checked back against the stored review.

Two deliberate properties:

- **No privileged content.** The document carries identifiers, counts and kinds
  only — never a record title or mark name. A printout left on a desk does not
  disclose what the firm is working on. Asserted directly.
- **Values are escaped, not interpolated.** A stale-source name or
  incompleteness reason is server-supplied text going into markup.

An empty exception list prints *"None recorded at generation."* rather than
omitting the section: an absent section reads as an omission, a stated "none"
reads as a check.

## The outcome reported is the outcome that happened

The document is produced first. Only if that succeeds is `generated` recorded.
If production throws, `failed` is recorded with a redacted reason that names no
record, and **the returned failure record is kept and shown** rather than
discarded in favour of a toast — because that recorded failure is what blocks
sign-off, and the user needs to see why they cannot sign.

A signed review is not offered an export control at all: the API refuses
re-export of a signed review, so the control is absent rather than present and
failing.

## A second capability-gate error, in a new place

Increment 8 fixed sign-off being gated on `ip:review` instead of `ip:approve`.
Recording an export is `ip:write`, but the control review card renders for any
`ip:read` member, so the export button was initially offered to read-only
members. Fixed and folded into the same gate test, which now asserts a
read-only member sees neither sign-off nor export.

That is twice in two increments. The pattern is that a card's own capability is
not the capability of every control inside it, so each control now states its
own.
