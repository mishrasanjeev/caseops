# IPLF-039C rebuild — increment 1: signed-off daily docket control review

**Slice:** `IPLF-039C`
**Date:** 2026-08-15
**Scope of this increment:** `CAL-OPS-09` and `CAL-OPS-13`, covering `UJ-59`
(4 paths) and `UJ-50-EXC-01`.

## Why a rebuild

The 2026-08-15 inspection audit found this slice largely unbuilt — roughly 4 of
22 paths — while recorded `implemented / passed / deployment_verified`. Most
notably `UJ-59` requires the daily docket control report to be *produced **and
signed off***, and **no sign-off step existed at all**. Patching around that was
not possible; the review had to become a real record.

## What this increment adds

A durable `ip_docket_control_reviews` record, so a report becomes reviewable
evidence rather than a transient projection.

| Behaviour | How |
|---|---|
| Generation time, filters and freshness visible (`CAL-OPS-09`) | The review stores `generated_at`, the exact `filters` used, and a `freshness` block naming stale sources and failed queries. |
| Sign-off | `POST /control-reviews/{id}/sign-off` records signer identity, label snapshot and timestamp, fenced on `expected_version` and terminal once signed. |
| Incomplete review cannot be signed (`UJ-59-EXC-01`) | Any stale source or failed query sets `completeness_status="incomplete"` with typed reasons; sign-off returns `ip_control_review_incomplete`. |
| Export failure blocks completion (`UJ-59-EXC-03`) | A recorded `failed` export returns `ip_control_review_export_failed` on sign-off; a successful regeneration clears it. |
| Restricted work leaks nothing (`UJ-59-EXC-02`, `UJ-50-EXC-01`) | Counts and exceptions derive from the access-filtered listing, so an unauthorised reviewer's report counts only what they may open and the restricted id and title appear nowhere. |
| Exceptions cannot be hidden (`CAL-OPS-13`) | Mandatory exceptions are computed at generation and **stored on the review**. A filter that plainly excludes a record still reports its exception, re-reading cannot drop it, and signing off does not clear it. |

The manifest hash covers generation time, filters, counts, exceptions and
incompleteness reasons, and is proved stable across sign-off — the artefact
signed is the artefact produced.

## Database-level enforcement

The service rules are duplicated as check constraints so the state is
unreachable even outside the service:

```sql
signed_off_at IS NULL OR (completeness_status = 'complete' AND export_status <> 'failed')
signed_off_at IS NULL OR signed_off_by_membership_id IS NOT NULL
```

## Ownership

Classification: **NEW** record, **EXTEND** of the existing report.
`ip_docket_control_report` and `list_ip_dockets` remain the canonical
projections; the review stores their output plus review state and creates no
second docket, coverage or deadline owner. Access is inherited from
`list_ip_dockets`, so no second access path exists.

## Increment 2 — the daily docket (UJ-50, all 5 paths)

`GET /api/ip/daily-docket`, read-derived from the access-filtered listing.

| Path | Proven behaviour |
|---|---|
| `UJ-50-NORMAL` | Per-owner workload and capacity: assigned, critical and unacknowledged counts, active flag and `capacity_state`, with generation time and filters visible. |
| `UJ-50-EXC-01` | A restricted docket adds no queue entry and no count; a member without access sees a smaller total and neither the id nor the title. |
| `UJ-50-EXC-02` | A deactivated owner escalates to the named backup by id; with **no** backup the item is reported `unowned` rather than quietly dropped. |
| `UJ-50-EXC-03` | With a stale source the affected counts are `null`, never `0` — the test asserts `assigned_count is None` *and* `!= 0`. The owner still appears, so the work does not vanish from the view. |
| `UJ-50-EXC-04` | A critical coverage that is reassigned and not re-acknowledged escalates with `reason="unacknowledged_critical"` and names the backup. |

Criticality is joined from `IpDeadline.is_critical` through `matter_deadline_id`
rather than re-declared, so there is no second definition of "critical".

## A regression this caught in the existing suite

The batched regression failed `test_ip_prd_slices.py::test_ip_remaining_operations_end_to_end`
after the reassignment access fix. Investigation showed the guard was **correct**
and the existing test was encoding the defect: its docket is `restricted: True`
and its replacement is a directly-inserted membership with no access grant, yet
it asserted the bulk transfer returned 200 and that the database showed the
walled-off member as responsible.

The test now asserts the refusal and that every coverage row is byte-identical
before and after, in the API response and in the database. The success path is
covered separately by
`test_ip_coverage_reassignment_access.py::test_uj57_bulk_transfer_succeeds_when_the_replacement_has_access`,
so no coverage was lost. **The guard was not weakened to make the suite pass.**

## Increment 3 — the reassignment workflow (UJ-57, remaining 5 paths)

CAL-OPS-08 requires an atomic preview **and** an accepted replacement or
approved emergency coverage. Reassignment previously moved ownership
immediately, so critical work could be handed to someone who never accepted it.

Migration `20260815_0002` adds `pending_replacement_membership_id`,
`replacement_decision`, `replacement_decided_at`, `replacement_decision_reason`,
`emergency_until` and `emergency_escalation_membership_id` to
`ip_deadline_coverages`. Existing rows default to `replacement_decision='none'`,
so current ownership is preserved exactly.

| Path | Proven behaviour |
|---|---|
| `UJ-57-NORMAL` | Preview returns the affected coverage and docket ids, an access verdict, and a 64-character token. Proposing marks the row `pending` and **leaves the current owner in place**; only the replacement's acceptance moves ownership, and exactly one coverage row exists throughout. |
| `UJ-57-EXC-03` | A rejection returns the work to the original owner — never unowned — records the reason, is terminal against replay, and only the **named** replacement may decide (403 otherwise). |
| `UJ-57-EXC-04` | Adding another coverage after the preview invalidates the token; the proposal is refused with `ip_coverage_preview_stale` and neither row is touched. A fresh preview covering both rows succeeds. |
| `UJ-57-EXC-05` | Emergency cover transfers immediately but is refused without an escalation owner and refused if the expiry is already past. When granted it records `emergency_until`, the escalation owner, and status `emergency`. |
| `UJ-57-EXC-06` | Every pre-existing audit row is byte-identical after the transfer: history is appended, never rewritten. The acceptance is attributed to the replacement and is proved not to be backdated to the original owner. |

Two rules are enforced in the database as well as the service: a `pending`
transfer must name who it waits on, and emergency cover must carry an escalation
owner.

### Semantic change worth noting

`reassign-propose` no longer transfers ownership. The pre-existing
`bulk-reassign` route still transfers immediately, so the two now differ. That
is deliberate for this increment — bulk-reassign retains its access guard from
the earlier fix — but the routes should be reconciled before release so there is
one transfer semantic, not two.

## Still unbuilt on IPLF-039C

This is **increment 3 of at least four**. Untouched:

- `CAL-OPS-09`'s saved team queues and bulk acknowledgement with per-record
  validation — the daily docket reports workload but cannot yet persist a queue
  or acknowledge in bulk.
- Reconciling `bulk-reassign` with the new propose/accept semantics so there is
  a single transfer path.
- `UJ-62` (6 paths) — external calendar projection is still a bare pointer with
  no times, no retry, no revocation handling, no redaction and no date-only rule.

`implementation_status` therefore stays `in_progress` and `release_status`
stays `blocked`. `CAL-OPS-07`, `08` and `10` are not claimed; `CAL-OPS-09` and
`CAL-OPS-13` are advanced but not closed, because the daily-docket half of
`CAL-OPS-09` — saved queues, capacity, bulk acknowledgement — is not built.
