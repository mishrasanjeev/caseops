## Delivered behavior

- Added Alembic head `20260807_0003`, lifecycle columns/checks on the docket,
  and the tenant-scoped `ip_docket_events` table.
- Added typed event schemas and one command service for append, list, and
  active/terminal transition operations.
- Serialized event sequence creation under the parent lock and rejected stale
  lifecycle versions.
- Preserved original events; corrections/reconciliations create linked rows
  and registry facts remain candidates until an explicit decision.
- Enforced same-tenant docket/application/proceeding/membership ownership and
  same-docket correction/reconciliation links.
- Acquired Matter before docket locks so direct IP lifecycle transitions and
  Matter disposal cannot race in opposite lock order.
- Made ordinary docket and child operations fail closed for terminal parents;
  generic version/metadata commands cannot reactivate a record.
- Atomically neutralized active coverage, open related-right obligations, and
  their shared open deadlines on terminal transition. Controlled reopen leaves
  those children neutralized.
- Extended Matter disposal to archive linked IP dockets consistently, append a
  system lifecycle event, increment lifecycle versions, and neutralize IP
  operational children in the same transaction.
- Exposed lifecycle fields in existing docket responses without adding a
  lifecycle route or enabling a production feature. IPLF-022B owns the
  capability-gated user workflow and exceptions.

## Rollout and rollback

The production migration is additive except for deterministic normalization of
already-archived docket activity flags. It neither invents a legal event for
historical records nor activates a feature. Mixed revisions remain compatible:
new response fields are additive, old writers receive server defaults, and
Matter disposal was upgraded with the constraint in the same candidate.

Before any production write, downgrade/re-upgrade is proven. After event writes,
rollback must preserve legal history through rollout-off and a forward fix;
destructive table removal is not authorized.

There is no arbitrary seven-consecutive-day scheduler gate. Release readiness
uses deterministic exact-revision checks and the genuine approvals relevant to
the behavior; none is fabricated here.
