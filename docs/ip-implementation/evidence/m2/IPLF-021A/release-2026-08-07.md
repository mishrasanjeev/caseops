## Delivered contract

- Added Alembic head `20260807_0001` and matching SQLAlchemy definitions for
  `ip_assets`, `trademark_applications`,
  `trademark_application_scopes`, `trademark_representations`,
  `ip_proceedings`, `ip_identifiers`, `ip_parties_and_roles`, and
  `ip_relationships`.
- Kept `ip_docket_records` as the lifecycle/access anchor. Every new legal
  record is tenant-linked to that anchor with composite company constraints;
  parties optionally link to the canonical tenant-scoped Client record.
- Added the supporting `clients(id, company_id)` unique key needed by the
  tenant-composite party foreign key. This does not create a second Client
  owner or writer.
- Preserved raw identifiers and stored a deterministic Unicode-normalized,
  case-folded, alphanumeric search value. Normalized collisions are searchable
  reconciliation candidates, not an unsafe uniqueness merge.
- Required identifier kind, office, jurisdiction, source, effective date,
  primary designation, and exactly one application/proceeding owner.
- Restricted application/registration identifiers to applications and
  opposition/rectification/appeal/court identifiers to proceedings.
- Modelled identifier corrections as immutable successor facts with a required
  superseded identifier and correction reason.
- Added an explicit filed-phase invariant: a current confirmed application
  number is required unless the source explicitly reports pending allocation.
- Added effective-date constraints for application scope, party roles,
  identifiers, and relationships; immutable representation versions; and
  tenant-scoped relationship constraints.
- Kept the schema dark and expand-only. IPLF-021B remains the sole owner of API
  commands, configuration persistence, reconciliation workflow, and UJ-01
  acceptance.

## Data safety, rollout, and rollback

The production migration is additive and creates empty tables plus a redundant
tenant-composite uniqueness key on existing Client identifiers. It does not
rewrite or infer an IP record from `ip_docket_records`; that reconciliation and
backfill proof belongs to the guarded IPLF-021B switch.

All IP entitlements and rollout flags remain disabled. Old application
revisions neither read nor write the new tables, so mixed-revision operation is
safe during this expand phase. Before deployment, the exact PostgreSQL CI
migration must pass. Rollback before any IPLF-021B writes is the tested
`20260807_0001 -> 20260804_0004` downgrade. After writes begin, rollback is
forward-fix/flag-off and export-preserving rather than destructive downgrade.
